# 使用流程紀錄：額度更新與 429

目的：在重寫更新規則之前，先把「實際使用時發生了什麼」完整記下來。
本文只記事實與疑點，不含新規則。標「已證實」的有檔案或畫面為證；標「推斷」的沒有實測。

## 一、目前所有會觸發更新的來源（依程式碼）

| 來源 | 位置 | 手動/自動 | 備註 |
|---|---|---|---|
| App 啟動 | `AppContainer.swift:60` | 自動 | 啟動時打一次 |
| 30 秒定時器 | `SnapshotStore.scheduleRefreshTimer` | 自動 | 每 30 秒檢查，實際是否送出由 `shouldFetch` 決定 |
| 網路恢復 | `networkChanged(online:)` | 自動 | 清掉 60 秒失敗暫停，再判斷一次 |
| 喚醒睡眠 | `systemDidWake`（延遲 4 秒） | 自動 | 同上 |
| 面板上的重新整理鈕 | `DashboardView.swift:116` | 手動 | 15 秒節流 |
| 選單的重新整理 | `StatusItemController.swift:174` | 手動 | 同上 |
| OpenCode | `AppContainer.swift:72` 走 `refreshNow` | 自動 | 只讀本機資料庫，不連網 |

## 二、每次是否送出，現在怎麼判斷（`shouldFetch`）

1. 沒追蹤、或正在更新 → 不送。
2. 429 冷卻中 → 不送（手動也一樣）。
3. 手動：Claude 距上次成功未滿 60 秒不送，其餘送。
4. 自動：失敗後 60 秒內不送；沒有快取就送；否則距上次成功需超過 max(設定間隔, 該家最短間隔)，Claude 最短 10 分鐘。

429 之後的冷卻：優先用伺服器的 `Retry-After`，沒有則 2、5、10、20、40 分鐘遞增。冷卻只存在記憶體，重啟即消失。

## 三、實際發生過的情境（時間線）

### 情境 A：重新連網後 Claude 變成「請求太頻繁」（使用者回報）
- 重連後卡片出現 429 訊息。當時舊版訊息只寫「稍後自動重試」，沒有時間。
- 當時的程式在有錯誤時會繞過手動節流，且重連後可能多次送出。已在後續版本修正。
- 疑點：重連時實際送了幾個請求，沒有紀錄（見第五節）。

### 情境 B：2026-10-27 晚間，卡片寫「伺服器要求等到 21:37」（已證實）
- 畫面：5H 89%、7D 36%，標「快取」。快取檔顯示 Claude 最後成功為 17:03。
- 使用者說中間關過網路。離線期間 App 不會送請求，所以 17:03 到重連之間沒有更新有一部分是正常的。
- 「伺服器要求」代表回應帶了 `Retry-After`，不是 App 自己算的退避。
- 結果：快取檔顯示 Claude 在 21:46 成功更新，比 21:37 晚 9 分鐘，代表冷卻結束後自動恢復。

### 情境 C：2026-10-28 早上，又是 429，這次要等到 10:11（已證實）
- 21:46 成功之後，到隔天 09:15 沒有新的 Claude 成功紀錄。夜間 Mac 可能睡眠，推斷，未證實。
- 09:16 的畫面：5H「84% · 0m」、7D 34%，標「快取」，訊息「伺服器要求等到 10:11」，約 55 分鐘。
- 5H 的重置時間早已過去，卡片卻仍顯示 84%，舊數字被當成現況。這是顯示上的缺陷。
- 09:37 使用者按重新整理仍沒有額度。原因是 429 冷卻中，手動被略過，按鈕沒有任何回應。

### 情境 D：5 小時窗口的定義（使用者提問）
- 依公開說明，5 小時窗口從窗口結束後的第一則訊息才開始，不是連續滾動。窗口未開始時伺服器不給重置時間，App 顯示「可用」。
- 這是依公開資料與程式處理方式判斷，沒有對伺服器實測。

## 四、使用者提出的問題（對規則的要求）

1. 重新連網後仍要等 10 分鐘太久（Claude 最短間隔）。
2. 手動重新整理在冷卻中被直接略過，且沒有任何回應。
3. 一個小時都讀不到額度，不應該這樣設計。
4. 過期的舊數字不應被當成現況顯示。
5. 規則應重新整理，而不是一層一層補。

## 五、已知缺口與未證實的事

- **沒有請求紀錄：** `QUOTABAR_LOG=1` 的輸出導到檔案時被系統緩衝，沒有寫出來；斷網時請求失敗也不會印。所以「重連後到底送了幾個請求」至今沒有證據。
- **冷卻不跨重啟：** 重啟 App 會清掉 429 冷卻，馬上再打一次。
- **限流來源不明：** 是伺服器對 token 的限制、Claude Code 同時使用同一個 token，還是我們造成，無法區分。社群回報顯示這個端點會長時間限流，`Retry-After` 常為 0 或缺少。
- **圓環大數字：** 過期時只調暗，仍顯示舊百分比。
- **其他家：** Antigravity 在 09:37 仍有更新，代表 App 本身沒有卡住，問題只在 Claude。

## 六、重寫前還需要補的資料

1. 一次完整、有紀錄的「斷網 → 重連 → 等待」，確認重連後送出的請求數與回應。
2. 失敗請求也要寫進日誌（目前只記有回應的）。
3. 確認 Claude 429 是否和 Claude Code 同時使用有關。
